Ogre / Patching
Patching

Patch verified Ogre targets only

Use the same Antenni helper layer as Lake, but keep separate GML files, target names, and compatibility checks for Ogre.

Separate game-specific patch code

assets/
`-- code/
    `-- ogre/
        |-- shop_price_patch.gml
        `-- controller_step_patch.gml

Do not put Lake and Ogre patch bodies in one ambiguous file. Clear separation makes reviews, conflicts, and update fixes easier.

Require and patch

const string target =
    "REPLACE_WITH_VERIFIED_OGRE_CODE_ENTRY";

context.RequireCodeEntry(target);
context.AppendCodeFromFile(
    "code/ogre/controller_step_patch.gml",
    target);

Use the placeholder only as structure. The real value must come from resource inspection of the current Ogre build.

Prefer narrow anchors

If you use FindReplaceCode, select an anchor that is unique but does not copy an entire decompiled function. Verify expected matches and stop the feature when the anchor changes.

Isolate new systems

When possible, create a uniquely named object and place it in a verified persistent room or attach it through one small existing hook. This is usually easier to maintain than replacing a central controller event.

Use unique names

obj_yourmod_controller
scr_yourmod_apply_patch
spr_yourmod_icon
snd_yourmod_alert
global.yourmod_enabled

Do not use Antenni's prefix for your own globals. Choose a stable prefix owned by your mod.

Failure policy

  • Missing required target: fail the mod with the resource name.
  • Missing optional target: log a warning and disable only that feature.
  • Unexpected replacement count: stop rather than applying a partial patch.
  • Unknown Ogre build: warn users and run your own compatibility checks.
Never fall back to a Lake target

A fallback strategy should try another verified Ogre anchor, not a similarly named resource from a different game.
