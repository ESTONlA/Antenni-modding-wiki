Ogre / Resources
Game research

Discover Ogre resources before writing patches

Objects, scripts, rooms, sprites, sounds, and code entries come from Ogre's current data.win. Record exact names instead of translating Lake examples.

Use a clean source file

Inspect the original Ogre data.win, not ANTENNI_CACHE_data.win. A cache already contains loader and mod changes and can give you false resource assumptions.

Resource categories to map

CategoryLook forRequire with
ObjectsControllers, player, UI, enemies, persistent systems.RequireObject
Code entriesCreate, Step, Draw, Alarm, and script implementations.RequireCodeEntry
Scripts/functionsReusable gameplay and UI logic.RequireScript or RequireFunction
RoomsMenu, gameplay, test, and transition rooms.RequireRoom
SpritesFrames, origin, collision masks, and animation sequence.RequireSprite
SoundsAudio groups, embedded files, and sound metadata.RequireSound
VariablesGlobals and instance fields referenced by target code.RequireVariable

Build a resource notebook

Feature: shop price change
Game: Ogre Chambers 2222
Game build/hash: ...
Object: ...
Code entry: ...
Anchor text: ...
Expected matches: 1
Other mods touching target: ...
Fallback if missing: disable feature

This turns reverse engineering into a reproducible compatibility record instead of a collection of guessed strings.

Verify from code

UndertaleCode code =
    context.RequireCodeEntry("REPLACE_WITH_DISCOVERED_CODE_ENTRY");

context.Log($"Verified Ogre target: {code.Name.Content}");

After a game update

Compare the new resource map and compatibility report with your notebook. A resource retaining its name does not guarantee its decompiled body or event assumptions stayed the same.

Document behavior, not only names

Write down why the target is correct, what code surrounds the patch anchor, and what visible test proves the patch still works.

Do not publish extracted game assets

Use game data for local analysis. Your mod release should contain your own code and assets, not redistributed game content.
